# 架构与产品边界

## 产品定位

签栖（Qianqi）是一个个人书签管理与浏览器首页应用。它将分类、书签、搜索、导入导出和备份能力放在一个轻量的服务端渲染应用中，优先保证可维护性、数据可迁移性和可信内网使用体验。

V1 的边界是单用户、单实例和 SQLite。项目不提供多租户隔离、在线协作、公共书签目录或公网身份体系；若要改造成公共服务，需要额外设计账户、授权、限流、审计和数据库并发能力。

## 运行结构

```text
浏览器
   │ HTTP
   ▼
FastAPI 应用
   ├─ 页面路由与 Jinja2 模板
   ├─ HTMX 局部交互与静态资源
   ├─ Session / CSRF / 安全响应头
   ├─ SQLAlchemy 数据访问
   └─ Alembic 数据库迁移
          │
          ▼
       SQLite 数据库
```

应用启动不会隐式创建或升级数据库。部署和升级由运维流程显式执行迁移，并在升级前保留可恢复的备份。

## 主要数据能力

- 分类与书签的创建、编辑、排序和软删除。
- 回收站恢复与永久删除。
- 浏览器书签 HTML、CSV 等格式的导入与导出。
- SQLite 一致性备份、保留策略和受控恢复。
- 乐观版本校验，避免并发编辑覆盖较新的数据。

## 安全边界

- 修改状态的请求使用 CSRF 保护。
- Session Cookie 使用固定名称，并配置 HttpOnly、SameSite 和按环境启用 Secure。
- 生产环境关闭 OpenAPI 文档端点。
- 日志不记录密码、Cookie、CSRF Token 或上传正文。
- 默认不请求第三方 favicon；远程 favicon 必须显式启用。
- 上传大小、导入行数和备份路径均受配置限制。

## 部署方式

项目提供三类可复用材料：

1. 本地 Python 开发运行。
2. Docker Compose 可信内网部署。
3. 使用单文件可执行产物的低资源 VPS 部署。

所有部署都应使用独立的数据目录和备份目录，不把真实 `.env`、数据库或备份提交到 Git。生产环境上线前应完成迁移、备份恢复和浏览器回归验证。

## 已知限制

- V1 只支持 SQLite，不适用于高并发或多实例写入。
- 当前默认是单用户模型；不要把它当作带账号体系的公共服务。
- 备份恢复会改变本地数据状态，应在维护窗口执行并保留回滚副本。
- 部署模板中的地址、端口、密钥和数据目录都必须按实际环境替换。
